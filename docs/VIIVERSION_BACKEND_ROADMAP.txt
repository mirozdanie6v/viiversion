============================================================
ARCHITECTURAL DECISION
============================================================

The first production architecture is NOT multi-tenant.

The `backend` branch is the reusable reference CORE only.
Every real client backend is derived from this core and then deployed independently.

For every client:
- separate Cloudflare Worker;
- separate Cloudflare D1 database;
- separate R2 bucket when required;
- separate KV namespace when required;
- separate Queues / Cron / Workflows when required;
- separate environment variables and secrets;
- separate Telegram bot token;
- separate payment provider credentials;
- separate domain/subdomain;
- separate migrations and production data;
- separate client-specific business schema and integrations.

There is NO tenant_id-based shared production database in this version.
There is NO shared runtime containing several clients.
Multi-tenancy is explicitly postponed until several separate production backends prove which components are genuinely common.

Reusable source code may be reused. Runtime data and credentials are isolated.

STAGE 5 — DERIVE THE FIRST CLIENT-SPECIFIC BACKEND
Status: NEXT
============================================================

This is the architectural boundary between reusable core and a real client application.

Required actions for the selected client:
1. Derive/create a client-specific backend from branch `backend`.
2. Give the Worker a client-specific name.
3. Create a separate client D1 database.
4. Replace the all-zero template D1 UUID only in the client configuration.
5. Configure the client's Mini App CORS origin.
6. Configure the client's Telegram bot token as a secret.
7. Keep all other clients completely absent from this runtime.
8. Create business migrations only for this client/domain.

============================================================
DEVELOPMENT PRINCIPLES
============================================================

1. Build production behavior, not demo-only backend behavior.
2. One client = one isolated backend runtime.
3. One client = one isolated production D1 database.
4. Never trust frontend price, role, payment state or Telegram identity.
5. Never commit bot tokens, API keys, payment credentials, raw sessions or production personal data.
6. Prefer Cloudflare-native services before external infrastructure.
7. Version all schema migrations.
8. Version API under `/api/v1`.
9. Auth/payment/security changes require tests.
10. CI must remain green before production deployment.
11. Reuse source code only after behavior is proven; do not share production state.
12. Multi-tenancy remains postponed.
