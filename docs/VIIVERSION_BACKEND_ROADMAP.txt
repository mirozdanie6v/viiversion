VIIVERSION BACKEND — ROADMAP
Version: 1.1
Date: 2026-09-09
Branch: backend

ARCHITECTURAL DECISION

The first production version is NOT multi-tenant.
Each client receives a separate isolated backend deployment.

For every client:
- separate Cloudflare Worker;
- separate Cloudflare D1 database;
- separate R2 bucket when file storage is required;
- separate KV namespace when cache/config storage is required;
- separate environment variables and secrets;
- separate Telegram bot token;
- separate payment provider credentials;
- separate domain/subdomain and deployment pipeline;
- separate migrations and production data.

Reusable code may be copied/extracted into common packages later, but clients do not share runtime databases, secrets, queues or business data.

TARGET STACK

- TypeScript
- Cloudflare Workers
- Cloudflare D1
- Cloudflare R2
- Cloudflare KV
- Cloudflare Queues / Cron Triggers / Workflows where required
- Telegram Bot API / Telegram Mini Apps initData validation
- REST JSON API
- Hono
- Zod validation
- Drizzle ORM for D1
- Vitest for automated tests
- Wrangler for local development, migrations and deployment

DEVELOPMENT PRINCIPLES

1. Build production behavior, not demo-only backend behavior.
2. Never trust prices, roles, payment state or Telegram identity from the frontend.
3. Keep each client's production data isolated.
4. Prefer simple Cloudflare-native services before introducing external infrastructure.
5. Do not introduce multi-tenancy until several separate client deployments prove which components are genuinely common.
6. Every stage must have acceptance criteria before moving to the next stage.
7. No secrets, bot tokens, API keys, payment credentials or production personal data in git.
8. Schema migrations are versioned.
9. API is versioned under /api/v1.
10. Changes to payments/auth/security require tests.
