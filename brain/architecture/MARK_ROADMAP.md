## M0B — Передача доступного контекста при вызове Марка

**Статус: PENDING VERIFICATION; пассивная подписка не требуется.**

При явном вызове Марка в обычном чате ChatGPT требуется передать в Mark Brain **тот контекст, который ChatGPT фактически предоставил инструменту**. Марк находится вне чата: после подтверждённого сохранения принятого контекста в оперативной памяти D1 он самостоятельно осмысляет и развивает знания; информация из другого чата становится доступной при следующем разрешённом вызове.

**Приёмка:** в чате A создать контрольные факты/решение/вопрос → один раз вызвать Марка → записать реальный вызов и сравнить предоставленный payload с эталоном → получить receipt и независимо восстановить сохранённое из Brain → проверить тот же контекст при явном вызове из чата B. Отдельно проверить дедупликацию, перезапуск, запрет чужого scope и честную фиксацию неполного/неизвестного покрытия. Наличие подключённого MCP/GitHub не доказывает автоматическую передачу полной истории. Не требовать получения новых сообщений чата без следующего вызова.

**Контракт:** [CHAT_CONTEXT_HANDOFF_CONTRACT.md](CHAT_CONTEXT_HANDOFF_CONTRACT.md). Если модель ChatGPT не передала нужные сведения, фиксируем объём реального payload и ограничение, а не утверждаем 100% полноту.

**Влияние на этапы:** отсутствие «пассивного мониторинга» больше не блокирует архитектуру. M3 зависит только от проверенного invoke-time handoff. Механизм внутренней памяти M1/M2 можно разрабатывать независимо от этой интеграционной проверки.

## M1 — Identity Core и постоянная память

**Задачи:** версионируемая защищённая идентичность с founder approval; Self-Model; знания с типом, достоверностью, происхождением, history, supersedes, review policy; адаптация существующей D1 без новой базы. Сохранить legacy commitments/decisions и совместимость API.

**Приёмка:** чистый запуск восстанавливает актуальные Identity Core и durable knowledge; неверное утверждение пересматривается без потери истории; несанкционированное изменение прав блокируется. Выполняется в staging и production после review/migration backup.

## M2 — Оперативная память и единый жизненный цикл событий

**Задачи:** долговечно сохраняемый прием событий, idempotent receipt, semantic frame, correlation, decision classification, рабочий контекст дня и чата, projection/summary history, персистентность per-run/per-session checkpoints. Сначала тестировать независимым авторизованным событием, не симулируя автоматизм ChatGPT.

**Приёмка:** одно сообщение проходит Receive → persist → understand → verify → update working context → candidate lasting memory; после перезапуска результат доступен; duplicate/out-of-order and concurrent writes do not corrupt context; тестовый ошибочный шаг восстановлен без дублирования.

## M3 — Вызов Марка из чата и смысловая обработка доступного контекста

**Зависимость:** успешная M0B и готовая запись/восстановление оперативной памяти M2.

**Задачи:** разрешённый вызов из обычного ChatGPT, аутентификация источника и области, передача фактически предоставленного контекста без ручного копирования текста, durable receipt, хранение в общем корпоративном рабочем контексте со scope чата, семантический отбор, обновление знаний и последующее чтение из другого разрешённого чата. Марк обрабатывает контекст **в собственной системе вне чата**, а не требует непрерывно наблюдать за перепиской.

**Приёмка:** в чате A созданы контрольные данные и выполнен один вызов → переданные данные без потерь сохранены в Brain → в чате B после явного вызова доступны подтверждённые факты и решения A → после restart запись сохранилась → отсутствие нового вызова из A не выдаётся за автоматическую синхронизацию → неизвестная полнота всей истории явно помечена.

**Гарантии:** полнота **полученного payload** и его сохранения проверяется независимо от полноты **всей истории ChatGPT**, которая не предполагается автоматически. Применяется [контракт передачи](CHAT_CONTEXT_HANDOFF_CONTRACT.md).

## M4 — Живой реестр и внутренние источники

**Задачи:** schema and relations registry with source attribution, source adapters GitHub / Linear / Drive; on-demand read; source cursor / incremental change observation; reconciliation of stale/missing updates; событие планирования новой сущности из чата не объявляется её deployed реализацией. Первичное заполнение начинается только после доказанного механизма изменения реестра.

**Приёмка:** добавление/изменение модуля обновляет реестр с доказательством; проверка GitHub/Linear/Drive видит новую информацию по запросу; source outage produces stale status not fabricated fresh observation; никакого wholesale copy commits.

## M5 — Мышление, обучение и управленческие действия

**Задачи:** полный CEO цикл Audit → Diagnose → Strategize → Organize → Assign → Measure → Correct → Learn с evidence-backed critic/verification; learned updates в Self-Model и знаниях, права на задачи, внешние reversible actions по матрице; founder approvals для коммерческих/необратимых/identity changes.

**Приёмка:** Марк обнаруживает конфликт, предлагает решение, получает данные, выполняет разрешённую операцию, проверяет эффект и корректирует память; нельзя объявлять выполненным неподтверждённое; запрещённый запрос отклоняется.

## M6 — Системная устойчивость и допуск к эксплуатации

**Задачи:** проверка параллельных независимых чатов/задач, перезапусков, конкурирующих обновлений, пропуска/повторной доставки событий, истечения credential, восстановления D1, прав доступа, минимизации и хранения данных, журналов; журнал бизнес-решений не теряется.

**Приёмка:** сквозной показ подтверждённого пути подключённый чат A → общая оперативная память → проверка источника → постоянная память/реестр → безопасное решение → подключённый чат B; независимые run checkpoints; восстановление после injected fault; source freshness and permission tests; формальный acceptance и rollback evidence.

## Правила переходов и контроля

- У каждого этапа — ограниченный scope, входные зависимости, acceptance tests и фактические ссылки на GitHub/Cloudflare/первоисточники.
- Отдельно учесть технический долг: существующий global checkpoint (id=1), ограниченный CEO audit→diagnose, отсутствие реестра и автопотока из чатов. Их нельзя описывать как исправленные заранее.
- Сначала согласованный контракт и доказанный lifecycle на одном событии, затем подключение источников. Не строить заново всю инвентаризацию ради закрытия статуса.
- Безопасные исправления действующего runtime допустимы отдельно, без переобозначения stage.
- Для контроля исполнения — Linear; для окончательных стандартов и их истории — GitHub; живой контекст — D1.
- Итоговое слово ACCEPTED для **архитектурного проекта** не эквивалентно ACCEPTED для **работоспособности Марка**. Все M1–M6 ожидают собственные проверки.
