# MARK — контракт передачи контекста при вызове в ChatGPT v1.0

**Статус:** ACCEPTED как целевой контракт (2026-10-27); **исполнение:** NOT IMPLEMENTED / integration proof PENDING.
**Основание:** уточнение владельца: Марк вызывается в выбранном чате; доступный при вызове контекст передаётся Марку и становится его оперативным контекстом; дальнейшие мышление, отбор и память принадлежат внешнему Brain, а не чату.
**Нормы:** [Architecture](MARK_ARCHITECTURE.md), [Roadmap](MARK_ROADMAP.md), [ADR-0001](ADR-0001-unified-mark.md).

## 1. Требуемое поведение

1. Пользователь намеренно **вызывает Марка в конкретном обычном чате**; вызов запускает передачу доступного для данного вызова контекста через разрешённое средство интеграции.
2. Средство передаёт **фактически предоставленные ChatGPT данные**, а не приписывает себе чтение всей истории, если API этого не подтверждает.
3. Внешний Mark Brain удостоверяет источник/область, регистрирует receipt, идемпотентно сохраняет полученный контекст в своей **оперативной памяти** (Brain D1) и выдаёт receipt с указанием зафиксированного объёма.
4. Уже **вне чата** Марк может анализировать сохранённый контекст, находить сущности/решения/задачи, сопоставлять с постоянной памятью и первоисточниками, обновлять оперативный контекст, а значимые подтверждённые знания переносить в постоянную память в рамках полномочий.
5. При следующем **явном вызове** в этом или другом разрешённом корпоративном чате он читает прежний контекст из Brain. Отсутствие нового вызова **не гарантирует** передачу последующих сообщений первого чата.

**Не требуется:** пассивная подписка Марка на каждое сообщение чата или фоновый перехват всей переписки. **Не допускается:** утверждать, что выбранное MCP-приложение автоматически получает весь transcript от ChatGPT.

## 2. Разграничение гарантий

**Разрешённое предположение:** ChatGPT может вызвать инструмент с переданными параметрами/содержимым, доступным модели при вызове. **Непроверено:** какая именно часть исторического контекста автоматически включается в конкретный вызов, доступны ли исходные message IDs и можно ли восстановить усечённые сегменты. Получаемый payload может быть выборкой или модельным изложением, а не полным transcript.

**Контракт полноты:** Mark обязан сохранять:
- `provided_context` — то, что действительно передано инструменту; оригинал payload или допускаемый политикой защищённый evidence_ref;
- `capture_kind` — `verbatim`, `structured_excerpt`, `model_summary` или `unknown`;
- `coverage` — `verified_complete_for_declared_scope`, `partial` или `unknown` с обоснованием;
- `available_scope` — границы переданного окна/сообщений, если доступны; иначе `unknown`;
- `source_ref` / `chat_scope_ref` — только при наличии разрешённого достоверного идентификатора. **Нельзя подменять фактический идентификатор чата идентификатором, придуманным моделью.**

**Правило:** successful receipt + сохранённый payload ≠ доказательство полноты истории чата. Если полнота не доказана, Марк отмечает `coverage=unknown/partial` и при ответе не утверждает, что знает всё обсуждение.

## 3. Интерфейс интеграции

Предпочтительный бизнес-контракт операции: `ingest_invocation_context` (название условное, не утверждение о готовом MCP action).

Input (логическая схема):
- `invocation_id` / `idempotency_key` — уникальный идентификатор повторного вызова;
- `source=chatgpt`, `received_at`;
- `principal_id` / `authorized_scope` — удостоверяются сервером, не выводятся только из текста;
- `conversation_ref` если подтверждённо доступен, иначе временный явный session scope;
- `context_payload` — доступная в вызове информация, разрешённая для записи;
- `capture_kind`, `available_scope`, `coverage_claim` (заявление инициатора, подлежащее проверке);
- `provenance`, `privacy_class`, `payload_hash`.

Output:
- `receipt_id`, `stored_at`, `working_context_revision`, `deduplicated`;
- `accepted_scope`, `coverage_assessment`, `processing_state` (`stored` / `processing` / `blocked`);
- `context_ref` для последующего получения актуальной оперативной памяти.

Важно: **сначала commit фактически принятого payload, затем ack**. Модельная интерпретация, сверка GitHub/Linear/Drive и долгосрочные знания могут обрабатываться позже внутри внешнего Brain. GitHub-мост может служить транспортом команд, но GitHub repo / PR / issue по умолчанию **не является местом хранения содержимого чата**. Данные контекста отправлять непосредственно в защищённый Mark Brain либо через разрешённый кратковременный транзит, без коммита приватных разговоров в репозиторий.

## 4. Приёмочное испытание (M0B / M3)

1. В обычном чате A разместить заранее известный контрольный контекст: 3 факта, 1 предложение, 1 явно принятое решение, 1 нерешённый вопрос. Вызвать Марка **один раз**.
2. Зафиксировать точный payload инструмента и серверный receipt. Сравнить каждый контрольный элемент с тем, что реально передано; отмечать пропуски и неопределённость. Нельзя считать «полнота 100%», если покрытие других старых частей переписки неизвестно.
3. Из нового запроса к Brain проверить сохранённый `context_ref`, классификацию `fact/proposal/decision/question`, `source_ref`, `coverage`; проверить отсутствие ложной активации утверждений.
4. В чате B **явно вызвать** Марка, получить от Brain сохранённый контекст A в рамках корпоративных полномочий и проверить точность решения и статусов.
5. Отправить в A сообщение **без нового вызова Марка**: его автоматическое появление в памяти **не требуется** и не считается провалом. При следующем вызове проверить, включено ли оно в фактически предоставленный контекст; если нет — отразить границу/пропуск.
6. Повторить идентичный вызов: результат не дублируется. Прервать обработку после receipt, запустить восстановление: данные не потеряны. Подставить недопустимого пользователя/область: запись отклонена.
7. Подтвердить работу после перезапуска Worker; отсутствующие метаданные не дорисовываются моделью, содержимое неподключённых чатов не извлекается.

**Критерий успеха передачи:** фактически предоставленный при вызове контекст принят и сохранён без потерь, корректно классифицирован и возвращён в другом разрешённом вызове. **Гарантия полной истории** допускается только если продуктовые интерфейсы предоставили проверяемый полный transcript/диапазон. Иначе `coverage=partial/unknown`.

## 5. Состояние

На 2026-10-27 указанный интерфейс, тестирование реального вызова и независимая фоновая семантическая обработка контекста **ещё не доказаны**. Наличие подключённого GitHub, открытого PR или защищённого Brain API сами по себе не доказывают работу передачи из ChatGPT.
