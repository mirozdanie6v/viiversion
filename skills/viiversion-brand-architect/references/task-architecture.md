# Task Architecture

This reference defines how VIIVERSION Brand Architect creates structures without
turning them into rigid templates.

## Universal sequence

For any new surface:

1. **Outcome** — what must this surface cause the audience to understand or do?
2. **Audience state** — what does the person know before arriving?
3. **Buyer job / decision** — what real decision are they trying to make?
4. **Relevant entities** — which canonical VIIVERSION entities can solve it?
5. **Commercial reality** — which of those are actually sellable/usable now?
6. **Proof plan** — what evidence can support each important claim?
7. **Narrative architecture** — what order minimizes confusion and perceived risk?
8. **Depth control** — when should technical/system detail appear?
9. **CTA** — what is the smallest useful next action?
10. **Brand QA** — validate before delivery.

The agent may change the order only when the channel or audience requires it.

## Homepage / parent-brand surface

Typical logic:

\`clarity → proof → relevance → scale → solutions → trust → depth → software → team → conversion\`

Do not force this pattern mechanically.

For viiversion.com, live Website Strategy / Homepage Architecture and decisions
control production constraints, current governance state, proof requirements and
known channel rules. They do **not** automatically control the new presentation
concept when the user explicitly asks for redesign or rejects the current
structure/copy.

### Homepage redesign mode

When the user says the current homepage is wrong, unclear, obsolete or should be
rebuilt while preserving only selected visual traits:

1. classify the task as REDESIGN, not AUDIT;
2. treat current homepage and legacy approved copy as OBSERVED_CURRENT;
3. extract hard constraints from L1-L3, L2/Proof and still-valid channel rules;
4. explicitly list which old presentation decisions are being challenged;
5. generate a fresh presentation concept from audience + buyer job + company
   truth, rather than restoring the previous Hero/sequence;
6. stress-test the new concept for five-second clarity before mapping it back to
   the website channel;
7. only after a concept passes synthesis + QA should it become a candidate
   Website Decision / Homepage Architecture change.

An approved old presentation can be superseded by a new candidate presentation.
Approval status is not a creative-quality score and must not be used as proof
that old copy is the best answer.

## Product / solution page

Default decision sequence:

1. What the buyer gets.
2. Recognisable trigger / situation.
3. Before → after.
4. How the workflow works.
5. What is included.
6. What can remain from the current stack.
7. Integrations / extensions only when relevant.
8. Proof.
9. Maturity / scope / price context from live source.
10. One next-step CTA.
11. Technical depth for buyers who need it.

Avoid feature dumping.

## Owned software page

1. Product category and actual use case.
2. Who uses it.
3. Core workflow.
4. Inspectable product behavior.
5. Maturity / distribution state.
6. Proof or live use.
7. Boundaries.
8. Access / install / beta / service route.
9. Technical or ecosystem detail.
10. CTA aligned with real external path.

Never publish internal roadmap as finished product.

## Industry / vertical page

1. Recognisable industry process.
2. The specific buyer jobs worth changing.
3. 1–3 relevant solutions, not the whole catalogue.
4. What each changes.
5. Relevant proof.
6. Existing-system compatibility.
7. Optional expansion path.
8. CTA.

Vertical = packaging, not new platform.

## Partner surface

1. Partner gap.
2. What VIIVERSION can supply without forcing a full agency replacement.
3. Delivery model / boundaries.
4. Relevant modules or owned software.
5. Proof.
6. White-label / co-delivery / specialist role where actually supported.
7. Commercial engagement path.
8. CTA.

Do not dump the whole product catalogue.

## Enterprise / CTO surface

1. Engineering problem.
2. Existing environment / constraints.
3. Capability and architecture.
4. Data / integration / DB / security implications.
5. Proof and team expertise.
6. Risk management and boundaries.
7. Delivery model: diagnostic / PoC / sprint / phased system / managed engineering.
8. CTA for technical discovery.

Here technical vocabulary may appear earlier than on SME surfaces.

## Profile / LinkedIn / company bio

1. Identity.
2. Engineering focus and outcomes.
3. Core capabilities.
4. Real proof or shipped classes of systems.
5. Owned software direction.
6. Specific role or CTA for that platform.

Do not turn profile into a product catalogue.

## Product launch / marketplace

1. One owned product.
2. One target user/problem.
3. Actual product workflow.
4. Demonstrable proof.
5. Differentiation grounded in behavior.
6. Maturity/access.
7. CTA: install / try / beta / join / buy.

Parent-company Engineering Solutions catalogue stays secondary.


## Market positioning / projection

1. Source entity and verified commercial state.
2. Market constraints.
3. Primary audience and buyer job.
4. Channel profile.
5. Language.
6. Goal.
7. Proof selection.
8. Projection: display name / headline / value proposition / CTA.
9. Metric and feedback capture.

Use `Entity × Market × Audience × Channel × Language × Goal → Projection`.
A market-specific projection cannot redefine the parent brand.

## GTM / distribution plan

1. Entity and product form.
2. Current sellability/readiness.
3. Current distribution fit from Distribution_Matrix.
4. Channel profile.
5. Current Launch Wave.
6. Current Distribution_Pipeline stage/blocker.
7. Choose one primary GTM motion.
8. Define next closed milestone.
9. Define KPI/outcome metric.
10. Define feedback destination.

Do not confuse a channel list with a strategy.

## Campaign / outreach sequence

1. Market + segment.
2. Buyer trigger/signal.
3. One primary entity/offer.
4. Proof.
5. Channel + language.
6. First-touch logic.
7. Follow-up sequence and stop conditions.
8. CTA.
9. Quota/cadence.
10. KPI.
11. Capture replies/outcomes as market signals.

For live execution refresh Sales Playbook, Sales_Router and Outreach_Queue.

## Software / plugin productization

1. Existing entity or candidate?
2. Target user/problem.
3. Repeatable workflow.
4. Generic functional contract.
5. Inputs/outputs and integration boundaries.
6. Install/use path.
7. Data/auth/privacy/support requirements.
8. Proof plan.
9. Distribution ecosystems.
10. Release/readiness gates.
11. Engineering implementation handoff.
12. Return completed implementation to launch/distribution loop.

Brand Architect owns productization and market contract, not fictional coding.

## Market feedback

1. Record observation.
2. Check whether it repeats.
3. Separate anecdote from pattern.
4. Connect pattern to metric/commercial outcome where possible.
5. Form validated learning only with sufficient evidence.
6. Create change request if strategy should be reviewed.
7. Never change L1-L3 automatically.

## Presentation / pitch

Build narrative around the decision the audience must make, not around internal
company sections.

Common flow:

\`context → problem/trigger → change → mechanism → proof → why VIIVERSION → engagement → next step\`

## Outreach

\`signal → relevant result → proof → low-friction CTA\`

One message should not explain company architecture.

## Proposal

Use VIIVERSION Proposal Studio when available.

Brand Architect supplies:
- seller identity;
- relevant entities;
- proof constraints;
- brand boundaries.

Proposal Studio owns:
- target research;
- diagnosis;
- win strategy;
- solution architecture;
- commercial model;
- proposal review and production.

## Audit / critique

When user gives existing material:

1. Identify intended audience and goal from the material/context.
2. Determine whether the user wants AUDIT or REDESIGN.
3. Check identity drift.
4. Check entity-level mixing.
5. Check claim/proof mismatch.
6. Check relevance and narrative order.
7. Check CTA.

If mode is AUDIT, report findings and the smallest correction.

If mode is REDESIGN:
- do not use the old canonical target as the answer merely because it is
  approved;
- diagnose why the old/current presentation fails the user's goal;
- produce a fresh presentation hypothesis;
- compare that hypothesis against hard brand/commercial/proof constraints;
- replace the broken structure rather than restoring an older one.

The default redesign output should contain:
- diagnosis of the current failure;
- new presentation principle;
- new structure/copy or concept;
- why the new solution is materially different;
- only unresolved blockers that truly require user input.
