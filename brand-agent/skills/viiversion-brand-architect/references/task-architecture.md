# Task Architecture

This reference defines how VIIVERSION Brand Architect creates structures without
turning them into rigid templates.

## Universal sequence

For any new surface:

1. **Outcome** — what must this surface cause the audience to understand or do?
2. **Audience state** — what does the person know before arriving?
3. **Buyer job / decision** — what real decision are they trying to make?
4. **Relevant entities** — which canonical VIIVERSION entities can solve it?
5. **Commercial reality** — which of those are actually sellable/usable now?
6. **Proof plan** — what evidence can support each important claim?
7. **Narrative architecture** — what order minimizes confusion and perceived risk?
8. **Depth control** — when should technical/system detail appear?
9. **CTA** — what is the smallest useful next action?
10. **Brand QA** — validate before delivery.

The agent may change the order only when the channel or audience requires it.

## Homepage / parent-brand surface

Typical logic:

\`clarity → proof → relevance → scale → solutions → trust → depth → software → team → conversion\`

Do not force this pattern if an approved channel architecture already exists.
For viiversion.com, live Website Strategy / Homepage Architecture and decisions
control the page.

## Product / solution page

Default decision sequence:

1. What the buyer gets.
2. Recognisable trigger / situation.
3. Before → after.
4. How the workflow works.
5. What is included.
6. What can remain from the current stack.
7. Integrations / extensions only when relevant.
8. Proof.
9. Maturity / scope / price context from live source.
10. One next-step CTA.
11. Technical depth for buyers who need it.

Avoid feature dumping.

## Owned software page

1. Product category and actual use case.
2. Who uses it.
3. Core workflow.
4. Inspectable product behavior.
5. Maturity / distribution state.
6. Proof or live use.
7. Boundaries.
8. Access / install / beta / service route.
9. Technical or ecosystem detail.
10. CTA aligned with real external path.

Never publish internal roadmap as finished product.

## Industry / vertical page

1. Recognisable industry process.
2. The specific buyer jobs worth changing.
3. 1–3 relevant solutions, not the whole catalogue.
4. What each changes.
5. Relevant proof.
6. Existing-system compatibility.
7. Optional expansion path.
8. CTA.

Vertical = packaging, not new platform.

## Partner surface

1. Partner gap.
2. What VIIVERSION can supply without forcing a full agency replacement.
3. Delivery model / boundaries.
4. Relevant modules or owned software.
5. Proof.
6. White-label / co-delivery / specialist role where actually supported.
7. Commercial engagement path.
8. CTA.

Do not dump the whole product catalogue.

## Enterprise / CTO surface

1. Engineering problem.
2. Existing environment / constraints.
3. Capability and architecture.
4. Data / integration / DB / security implications.
5. Proof and team expertise.
6. Risk management and boundaries.
7. Delivery model: diagnostic / PoC / sprint / phased system / managed engineering.
8. CTA for technical discovery.

Here technical vocabulary may appear earlier than on SME surfaces.

## Profile / LinkedIn / company bio

1. Identity.
2. Engineering focus and outcomes.
3. Core capabilities.
4. Real proof or shipped classes of systems.
5. Owned software direction.
6. Specific role or CTA for that platform.

Do not turn profile into a product catalogue.

## Product launch / marketplace

1. One owned product.
2. One target user/problem.
3. Actual product workflow.
4. Demonstrable proof.
5. Differentiation grounded in behavior.
6. Maturity/access.
7. CTA: install / try / beta / join / buy.

Parent-company Engineering Solutions catalogue stays secondary.

## Presentation / pitch

Build narrative around the decision the audience must make, not around internal
company sections.

Common flow:

\`context → problem/trigger → change → mechanism → proof → why VIIVERSION → engagement → next step\`

## Outreach

\`signal → relevant result → proof → low-friction CTA\`

One message should not explain company architecture.

## Proposal

Use VIIVERSION Proposal Studio when available.

Brand Architect supplies:
- seller identity;
- relevant entities;
- proof constraints;
- brand boundaries.

Proposal Studio owns:
- target research;
- diagnosis;
- win strategy;
- solution architecture;
- commercial model;
- proposal review and production.

## Audit / critique

When user gives existing material:

1. Identify intended audience and goal from the material/context.
2. Check identity drift.
3. Check entity-level mixing.
4. Check claim/proof mismatch.
5. Check relevance and narrative order.
6. Check CTA.
7. Replace the broken structure, not just describe problems.

The default audit output should contain:
- critical findings;
- corrected structure or copy;
- only unresolved blockers that truly require user input.
